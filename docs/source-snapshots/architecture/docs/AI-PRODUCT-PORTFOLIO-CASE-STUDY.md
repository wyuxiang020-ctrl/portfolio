## 1. 项目定位与完成度

建议名称：**AI 辅助开发的建筑作品集网站与交互式 3D 展示系统**。

一句话：以真实建筑作品的 PDF、图纸和 Rhino／SketchUp 模型为内容基础，通过 Claude Code 与 Codex 协作，将静态作品展示迭代成支持分层阅读、高清图纸查看和真实 3D 探索的网站，并建立资源、交互和模型质量的验收记录。

本案例的产品是“作品集网站”，ITB 迭代学习和祖母的火塘是其中两个深入整合的内容项目。建筑设计本身的研究、设计成果与网站产品开发应分别署名、分别评价。

## 3. 创作背景与问题定义

可用于作品集的背景表述：我已有建筑设计作品、调研、分析图、图纸、效果图与模型，希望形成独立网站，并将其作为进入 AI 产品方向的一次实际产品实践。早期借助 Claude Code 搭建网站，随着多轮修改，需求从视觉风格扩展到内容组织、加载速度、交互稳定性和模型展示，随后使用 Codex 继续检查与迭代。

从实际材料和需求可以归纳出四个问题：

1. **材料很多，阅读路径不清晰。** 长 PDF 将研究、推演与结果放在一个线性文件中；同一项目不同版本存在重复、待完成页和相似效果图。网站需要为快速浏览与深入理解提供不同层次。
2. **高清内容和加载成本发生冲突。** 图纸需要放大辨认，但直接把大图作为正文资源，会增加浏览负担。图片优化必须保留原始细节，而不是一律降低清晰度。
3. **二维材料难以自主探索空间。** 平面、剖面与效果图给出作者选择的视角，访客仍可能不理解结构和空间关系。原 CAD 文件又大，且通常要求专业软件。
4. **“页面能打开”不足以说明体验完成。** 滚轮冲突、关闭大图跳动、页面返回后重复绑定、模型失败没有恢复路径、公开链接失效，都会打断阅读。

网站潜在读者包括招聘者、设计评审、潜在合作者和非专业访客；维护者也是用户，需要可复用的内容与资产处理方式。这是根据使用场景提出的目标人群划分，尚未通过独立用户研究验证。

可作为后续验证的任务陈述：读者希望先快速判断项目是否值得深入，再查看支持设计判断的图纸和过程，必要时自主探索三维空间。当前不能声称已经验证“理解速度提高”或“求职转化提高”。

祖母的火塘原设计中的走访、家庭生活与空间研究属于建筑项目证据，不等于网站访客访谈。其“一天”内容属于设计情景推演，也不应写成真实访谈逐字记录或实际使用数据。

## 4. 产品结构与具体功能

阅读路径：**首页／作品列表 → 项目概述 → 调研与概念 → 推演与图纸 → 效果与实体模型 → 按需进入 3D → 返回继续阅读或联系作者**。

网站具有首页、作品列表、项目详情、About 和 Contact。详情页包含真实作品图文、章节入口、高清图库；ITB 和祖母的火塘额外包含完整 PDF 内容整合和末尾 3D。Contact 使用邮箱入口，不能描述成已有消息管理后台或 CRM。

### 图片与阅读

- 展示图片提供 480／960／1600px WebP 候选，不放大小图；设置宽高降低布局不确定性，正文懒加载与异步解码。
- 保留高清原图供点击查看；正文图库可切换，支持滚轮缩放、Escape 关闭、键盘打开及焦点返回。
- Banner 可独立打开单图，不混入正文图库。
- 关闭大图恢复阅读位置，导航离开清理监听器与观察器，减少重复初始化。
- 采用中文正文与图注、简短英文章节标题；补充研究与节点可以展开，主线优先呈现核心内容。
- 章节跳转避让固定导航；图片保持比例，图纸保留标题、标注及比例尺。

这里落实了图片懒加载和补充内容折叠，不宜写成正文虚拟化或所有文本都按需网络加载。

## 5. 技术栈与 AI 职责

| 层 | 当前技术与作用 |
| --- | --- |
| 页面与内容 | Astro 6、MDX、Tailwind CSS 4，静态页面及项目内容 |
| 交互 | JavaScript／TypeScript、PhotoSwipe 5 |
| 3D | Three.js 0.180、OrbitControls、GLTFLoader、GLB/glTF |
| 模型优化 | Meshoptimizer、GPU 实例复用、glTF Transform、Khronos glTF Validator |
| 图片 | Sharp、WebP、多尺寸资源、srcset/sizes |
| 材料与模型处理 | Python、rhino3dm、NumPy、Pillow、PDF 提取／渲染工具、已安装的 SketchUp C API |
| 版本和托管背景 | Git／GitHub、历史 Vercel 部署；当前版本以本地为准 |

没有采用 React Three Fiber 或 model-viewer；这些是早期候选方案。没有访客侧 LLM API、RAG、Agent、模型训练、业务数据库或对话后端。

实际工作流有两条：

**PDF → 阅读与比对 → 选择素材并记录来源 → 提取／渲染图片 → MDX 编排 → 响应式图片 → 浏览器检查。**

**CAD → 只读审计 → 导出工作副本 → 坐标／几何／材质修正 → 范围选择与压缩 → GLB 校验 → 浏览器交互 → 修正与回归。**

AI 在开发过程中协助读代码、整理材料、编写脚本、实现功能、定位问题和形成测试记录；网站运行时由确定性的代码处理按钮和相机操作。3D 几何来自用户模型，不能称为 AI 生成建筑。

## 7. 从 AI 产品经理角度可以归纳的工作

以下是把已发生的需求与取舍转写为 PM 语言，不表示你已独立编写全部技术实现或提前完成全部正式产品文档。

### 需求定义与优先级

你从图片效果、大图、滚动体验等具体问题出发，逐步提出性能基线、部署检查、真实 3D、完整内容及评测要求，并明确“一个一个完成”。这体现了先修基础体验，再补内容和复杂能力的范围管理。需要保存原始要求及实际执行顺序，而不是事后声称所有功能都是首版计划。

### 信息架构与内容质量

你要求按既有项目逻辑整合完整作品、删除重复、保留概念和分析，并将模型放到最后。对应的产品工作是组织“为什么做—如何推演—结果如何—如何探索”的阅读路径，以及控制内容密度。AI 完成具体提取、编排和文字初稿，设计含义与署名仍需你确认。

### 体验设计与异常流程

你关注关闭大图后的阅读连续性、Banner 独立查看和反复页面切换。产品需求因此从理想点击流程扩展到返回、重试、重置、退出与失败降级。加载进度、超时和释放资源是开发中形成的具体方案，可描述为协作补齐的体验，不能全部写成你最初逐项提出。

### 质量、性能与取舍

保留原图同时用轻量展示图；3D 在读者主动点击后加载；对重模型先检查范围与重复实例；不为减小体积盲目删除关键构件。这些是内容真实性、加载成本与探索深度之间的取舍。尚无用户数据证明方案最优，作品集应写清判断依据和待验证项。

### AI 协作和事实约束

你提供真实项目资料和模型，提出输出要求、修正方向及边界；AI 协助落实。产品上要求模型展示与原材料相符，不生成不存在的空间结论；当前自然语言功能还未实施。这比“使用 AI 写代码”更具体，但不能扩展为训练模型、优化模型准确率或部署智能 Agent。

### 验收意识

你提出加载、设备、成功率、任务测试和失败迭代要求。已形成资源基线、格式检查及本地交互记录；真人任务测试仍待开展。可以写“提出评测要求并借助 AI 建立工程验收记录”，不能写“已完成完整用户验证闭环”。

## 9. 值得展示的失败与修正

| 失败 | 修正 | 产品上值得记录的点 |

## 13. 可直接使用的作品集叙述

### 简介

我以自己的建筑设计资料为基础，主导了一个 AI 辅助开发的作品集网站项目。项目从静态图文展示出发，逐步补充了内容分层、高清图纸查看、图片加载优化和真实 3D 模型探索。我负责展示目标、需求优先级和验收要求，早期使用 Claude Code 搭建，后续借助 Codex 进行代码检查、内容整理、模型转换与测试。

### 问题与方案

原始内容分布在长 PDF 和较大的专业模型文件中，同一项目存在重复材料，读者需要在信息密度与理解成本之间切换。我将阅读路径组织为概述、研究、概念、推演、图纸和空间探索；正文采用响应式图片，保留原图供放大，补充研究折叠展示，3D 放在项目末尾并点击加载。

### 结果与验证

当前本地版本包含 7 个建筑项目，ITB 和祖母的火塘已从三份共 180 页 PDF 中整理出 95 张素材，并接入两个真实交互模型。ITB 网页模型约 6.2 MiB，支持 23 图层；祖母的火塘约 22.7 MiB，支持两组显示控制和五种视角。项目保留图片优化前后基线、模型格式校验及浏览器交互记录，修复了大图关闭跳动、重复初始化、图纸裁切与模型转换等问题。

### 反思与下一步

这次实践让我把视觉呈现要求扩展成具体的产品约束：内容必须有来源，交互需要覆盖退出和失败，性能结论必须注明统计条件，AI 生成的实现也要经过检查。目前 AI 主要用于开发协作；访客侧智能导览、真实用户任务验证和最新公开发布尚待完成。我会先验证现有按钮与阅读路径，再判断自然语言控制是否真正减少理解和操作成本。

### 简历措辞边界

若当前简历需要记录经历，可使用“AI 辅助开发实践／交互原型”名称，描述主导需求、组织真实资料和建立本地验收；依照此前约定，暂不作为已完成的第三个 AI 产品成果。后续完成 AI 和用户评测后再改写，不能提前填入准确率、用户数量、时间节省或线上成功率。
