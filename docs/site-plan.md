# 合并网站的内容与技术框架

> 2026-10-07 实施更新：本框架已落实为完整本地版本（16个内容页、3个产品案例、7个建筑详情）。采用Astro/MDX，AI正文转换为静态Astro，当前没有需要React水合的交互，因此未添加React。统一图库使用原生dialog，Three.js按需加载。实际状态见migration-checklist.md及qa/acceptance.md；本文以下保留原设计依据，线上域名切换仍是计划。

## 1. 一个身份，两组作品

用户已选择：AI 产品求职为主，建筑作品作为专业背景与能力证据。

首页定位建议：**王誉翔｜具有建筑与空间设计背景的 AI 产品实践者。**

辅助英文：AI PRODUCT · SPATIAL THINKING。

“AI 产品经理方向”可以继续作为求职目标。不要把个人 Demo 描述为商业上线产品，也不要将合作建筑项目的团队成果全部归为个人产出。

访客首先理解求职方向，再看到案例证据，最后深入建筑背景。首页直接展示精选项目，不设置必须先选择“建筑 / AI”才能继续的入口。

## 2. 网站结构

```text
yuxiangworks.com/
├── /                             综合首页，优先服务 AI 招聘阅读
├── /ai/                          AI 与数字产品项目总览，可直接投递
├── /projects/knowledge-copilot/   建筑项目知识助手
├── /projects/gym/                AI 健身与饮食记录
├── /projects/spatial-portfolio/  交互式建筑作品集的产品与实现案例
├── /architecture/                建筑与空间作品总览
│   └── /architecture/[slug]/     7 个现有建筑项目的独立详情
├── /about/                       专业背景、经历、个人贡献
├── /resume/                      完整网页版简历和 PDF
└── /contact/                     直接联系入口，延续旧地址
```

主导航：精选项目 / 建筑与空间 / 关于我 / 完整简历。联系方式放在导航按钮及页脚；避免新增空洞的“博客”“实验室”等栏目。

所有地址均为目标规划。旧地址逐条迁移，不把所有项目链接粗略跳到首页。

## 3. 首页的建议阅读顺序

| 区块 | 内容 | 表达重点 |
| --- | --- | --- |
| 个人定位 | 姓名、AI 产品方向、建筑背景、一句话关注的问题 | 第一屏能看出你在申请什么岗位 |
| 精选 AI 与数字产品 | 建筑知识助手、健身记录、交互式作品集三个案例 | 核心问题、个人责任、关键判断和案例入口 |
| 能力证据 | 引用追溯、多模态草稿确认、空间交互 | 每条能力连接到具体案例章节，不做无来源的技能评分 |
| 建筑与空间选集 | 2—3 个重点项目及“全部建筑作品” | 真实场景理解、研究、视觉与空间表达 |
| 关于与经历 | 教育、实习、方法和可到岗时间 | 从专业背景解释产品方向，避免重复长篇履历 |
| 简历与联系 | 网页简历、PDF、邮箱 | 招聘者可直接保存或联系 |

可以延续此前喜欢的深色、侧边定位与内容阅读布局。桌面使用侧栏，移动端转为紧凑顶部导航；中文是正文主体，英文用于栏目标签。建筑详情采用宽幅图文，AI 详情采用决策叙事，两者共用字体、间距、导航、按钮和图片浏览方式。

## 4. 两种案例模板

### AI 与数字产品案例

开头概览 → 问题与场景 → 核心流程演示 → 关键决策及舍弃方案 → 评测结果与限制 → 技术附录 → 证据与外部入口。

- 第一屏保留角色、项目阶段、目标问题、可验证入口。
- 结果数字说明分母、样本、条件、日期和局限；测试通过不等同于真实用户认可。
- 模拟数据、合成图片与真实界面分别标注。
- 详细过程与技术附录放在中段，完整证据入口放在末尾。
- 图片使用同一套全屏浏览：完整显示、序号、滚轮切换、最后一张提示、点击关闭、Esc、关闭后恢复焦点和原阅读位置。

### 建筑与空间案例

主视觉 → 项目背景和个人责任 → 场地 / 人群 / 需求 → 设计取舍 → 图纸及空间结果 → 可选 3D 探索 → 合作分工与反思。

保留 7 个现有项目：延续与重构、新五感设计、迭代学习、祖母的火塘、½ 日记、暂驻之间｜临时咖啡馆、「20+」青年集合住宅。

### 第三个 AI 案例的边界

“建筑作品与交互式 3D”继续作为数字产品案例，重点讲阅读层级、加载策略、失败恢复、交互验收和 AI 辅助开发。建筑栏目展示具体建筑设计本身。两处交叉链接，但不复制整段内容，也不把 AI 辅助开发直接称为 Agent 产品。

网站合并本身可成为这篇案例的一次迭代；只有真实实施、验证后才补充成果。

## 5. 实现框架

建议统一为 **Astro 静态站 + MDX 内容 + 必要的 React 交互组件**。

- 建筑站已有 Astro / MDX 基础，内容、图片处理和 Three.js 查看器可逐项迁移。
- AI 站的 React 组件可以经适配后继续使用；路由、`next` 专有导入、别名、共享样式和浏览器事件需要逐项核对。
- 首屏、正文、简历预生成 HTML，图库和模型按需运行；3D 模型不进入全站公共加载过程。
- 不需要为了合并新增数据库、AI API、后台账号系统或 MCP 服务。
- 个人资料集中在一个数据来源。可到岗时间沿用“2026.11 可到岗，可协商提前至 10 月”，不添加工作城市偏好；其他最新个人事实在迁移时与简历核对。
- 保留已公开的 `/downloads/`、`/evidence/` 等资源地址，或制定逐项替代关系。

本地公共资源盘点：建筑站约 594.3 MiB / 950 个文件，AI 站约 20.5 MiB / 31 个文件。这是本地 public 总量，不是单页下载量，也不是部署压缩包大小。应核对实际引用、派生图和模型变体后迁移，避免连同冗余资源全部塞入首页。

## 6. 域名和发布

最终建议：一个源码仓库、一个构建产物、一个主要托管项目；主地址使用现有 `yuxiangworks.com`。

```text
本地合并项目 → GitHub 保存版本 → 构建静态网站 → 腾讯云 EdgeOne 发布
                                                     ↑
Vercel 管理现有域名和 DNS → 将网站域名解析至托管服务 ─────┘
```

腾讯云作为目标托管是沿用已修复的 AI 站部署经验，不代表已经确认建筑模型在该平台上的全部表现。正式切换根域前，需要验证大文件限制、Range 分段请求、正确的模型 MIME 类型、缓存、移动端、境内实际访问和 HTTPS。

Vercel 可以继续承担域名与 DNS 管理，网站内容不一定必须托管在 Vercel。无需新买域名。根域切换、两个域名的证书和旧地址跳转都是独立上线工作，不会因复制文件夹自动完成。

当前 GitHub 推送不会自动更新 AI 站。合并后应明确接通 Git 集成或受控发布流程，并以“线上版本核验成功”为完成标准。具体授权范围在实际连接时核对。

`ai.yuxiangworks.com/` 最终跳到 `yuxiangworks.com/ai/`；原 AI 项目链接逐页跳到主域相同项目路径；原建筑 `/work/` 路径跳到 `/architecture/`。旧域名执行 HTTPS 跳转仍需有效证书。
